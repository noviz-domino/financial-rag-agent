# 청크 구조·메타데이터 선택지

> 현재(`structural_1200_fig`)는 **평면 구조**예요. 모든 청크가 독립적이고, 문서·페이지·순서·종류 메타데이터만 붙어 있어요.
> ⭐ = 추천, 💰 = AI 호출 비용 발생

## 선택지

| | 방식 | 검색 단위 → LLM 입력 | 우리 문서에 대입 | 비용 | 장점 | 단점 |
|---|---|---|---|---|---|---|
| A | 평면 (현재) | 청크 → 같은 청크 | 용어 / 조항 / 섹션 / 표 / 그림 | 0 | 단순 | 작은 청크는 문맥 부족, 큰 청크는 검색이 흐려짐 |
| ⭐B | **Parent-Child** (small-to-big) | 작은 child로 검색 → **parent**를 LLM에 | 조항 → 항(①②) / 반쪽 페이지 → 섹션·표·그림 / 그림·표 → 소속 페이지 영역 | 0 | 검색은 정밀하게, 답변은 문맥과 함께. 그림 청크가 주변 설명을 같이 가져옴 | parent가 길면 토큰 증가 |
| C | Sentence window | 문장으로 검색 → 앞뒤 N문장 | 약관 각 호, 가이드북 문장 | 0 | 숫자·조건 질문에 정밀 | 표·그림에는 안 맞음 |
| ⭐D | **이웃·참조 링크** | 청크 + 링크된 청크 | `prev/next`, 본문의 "그림 Ⅲ-5" → 그림 청크, 약관의 "제17조에 따라" → 해당 조항 | 0 | 다중 조항 질문에 강함. **Agent가 링크를 따라가는 도구**로 쓰기 좋음 | 링크 추출 규칙이 필요 |
| E | 계층 요약 (RAPTOR, 문서 요약 인덱스) | 문서·장 요약 노드 + 원문 | 문서별·장별 요약 | 💰 | "이 문서 전체에서…" 같은 넓은 질문 | 요약 생성 비용, 요약 환각 |
| F | Multi-vector (가상 질문·요약 임베딩) | 청크마다 "이 청크가 답하는 질문"을 생성해 임베딩 | 상황 서술형 질문 대응 | 💰 | 질문과 표현이 달라도 검색됨 | 청크 수만큼 LLM 호출 |
| ⭐G | 메타데이터 필터 (self-query) | 라우터가 `doc_type`·`content_type` 필터를 고름 | "표에서…" → `table`, 약관 질문 → `terms` | 0~💰 | 이미 있는 메타데이터 활용, 노이즈 감소 | 라우팅이 틀리면 정답을 놓침 |

## 추천: B + D + G (AI 비용 0, 규칙으로 만들 수 있음)

```
parent (LLM에 전달)                     child (임베딩·검색)
──────────────────────────────────────  ───────────────────────────────────────
용어 1개                                  = parent 그대로 (짧아서 나눌 필요 없음)
약관 조항 전체 (제17조)                    항 단위 ①②③ (길면), 짧은 조항은 그대로
반쪽 페이지 영역 (가이드북 p10 L)          섹션 텍스트 / 표 / 그림 각각
```

### 추가될 메타데이터
| 필드 | 예시 | 용도 |
|---|---|---|
| `level` | `parent` / `child` | 저장소 분리 (child = 벡터 인덱스, parent = 문서 저장소) |
| `parent_id` | `pc__terms06__a017` | child → parent 조회 |
| `child_ids` | `[…__a017__c0, …__c1]` | parent → child (분석용) |
| `prev_id`, `next_id` | 같은 문서의 앞뒤 청크 | 경계에서 잘린 문맥 보충 |
| `section_path` | `["재무설계 과정", "1단계 재무목표 세우기"]` | 문맥 보존, 제목 접두어 |
| `refs` | `["그림 Ⅲ-5 → fig__…p5__f0", "제17조 → …a017"]` | 다중 근거 질문, Agent 도구 |
| `source_ids` | parent와 동일하게 상속 | 평가 호환 (지금 지표 그대로 사용) |

### 평가 방법 (한 요소만 바꾸기)
| 실험 | 고정 | 변경 | 측정 |
|---|---|---|---|
| A vs B | 같은 청크 텍스트·검색기·k | LLM에 child만 vs parent | 답변 점수, **입력 토큰** |
| B + D | B | 링크 확장 on/off | 다중 근거 문항(Recall), 토큰 |
| G | B | 필터 on/off | Hit@k, 표·그림 문항 점수 |

## 정할 것
1. B(Parent-Child)를 기본 구조로 할지
2. D(링크)를 청킹 단계에서 만들지, Agent 단계에서 도구로 만들지
3. E·F(💰)를 실험 후보에 넣을지

### BM25 비교 (같은 검색기·같은 질문)
| 전략 | 기본 Hit@1 | 기본 Hit@5 | 기본 MRR | 가이드 Hit@5 | 추가 Hit@5 | 추가 MRR | LLM 입력 글자(top5) |
|---|---|---|---|---|---|---|---|
| recursive_500_50 | 0.483 | 0.683 | 0.561 | 0.85 | 0.883 | 0.748 | 2,258 |
| structural_1200_fig (평면) | 0.583 | 0.783 | 0.658 | 0.90 | 0.900 | 0.737 | 3,027 |
| parentchild_400 (child만) | 0.583 | 0.800 | 0.666 | 0.85 | 0.850 | 0.705 | **1,451** |
| **parentchild_400 [parent]** | 0.583 | **0.817** | **0.672** | 0.85 | 0.883 | 0.713 | 4,377 |
| parentchild_400 [filter hard] | 0.583 | 0.783 | 0.663 | 0.80 | 0.850 | 0.705 | 1,475 |

### 해석
1. **Parent로 접으면 근거 다양성이 올라가요.** 같은 조항의 child 여러 개가 top-5를 차지하던 문제가 사라져서 기본 Hit@5가 0.783 → 0.817이 됐어요. 대신 LLM 입력은 평면 구조의 1.45배예요. **답변 품질 향상이 이 토큰 증가를 정당화하는지**는 답변 평가 단계에서 확인해야 해요.
2. **child만 쓰면 입력은 절반**이지만, 추가 PDF에서 MRR이 떨어져요(0.737 → 0.705). 작은 청크는 BM25가 쓸 단어가 적어서예요. 임베딩 검색에서는 결과가 다를 수 있어요.
3. **hard 필터는 오히려 손해**예요(같은 구조끼리 비교: parentchild 가이드 Hit@5 0.85 → 0.80, 평면 구조 0.90 → 0.85). 규칙이 틀리면 정답이 후보에서 아예 빠져요. 그래서 기본값은 **scope(doc_type)만 강제하고 content_type은 제안(soft)** 으로 둬요(`suggest_filter(hard=False)`). 필터는 Agent가 "첫 검색이 실패했을 때 범위를 좁혀 재검색"하는 용도로 쓰는 게 맞아요.
4. 가이드 세트는 20문항이라 0.05 = 1문항이에요. 차이를 결론으로 쓰지 마세요.

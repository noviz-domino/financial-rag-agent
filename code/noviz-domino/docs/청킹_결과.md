# 청킹 단계 결과 (1차, BM25 기준)

## 실행 순서
```bash
python -m src.ingest            # 근거 단위(용어·조항·페이지) → data/processed/units.jsonl
python -m src.check_sources     # 정답 source_id 251개 연결 확인 (누락 0)
python -m src.loader            # 레이아웃 로더 → data/processed/pages_v2.jsonl
python -m src.chunking --strategy recursive --size 500 --overlap 50
python -m src.chunking --strategy structural --max-chars 1200 [--title]
python -m src.check_chunks      # data/chunks/*.jsonl 전부 비교 → data/chunks/compare_bm25.json
```

## 전략 정의
| 이름 | 입력 | 나누는 방법 |
|---|---|---|
| `recursive_{size}_{overlap}` | 문서 전체를 이어 붙인 텍스트(부록 제외) | `RecursiveCharacterTextSplitter`, 구분자 `\n\n` → `\n` → `. ` → `다. ` → 공백 |
| `structural_{max}` | 용어집·약관 = units, 가이드북·추가 = pages_v2 | 용어 1개 / 조항 1개(max 초과 시 ①② 항 단위) / 반쪽 페이지를 제목·글머리표 경계로 나눠 max까지 묶음. 표·그림 수치는 별도 청크 |
| `..._title` | 위와 같음 | `embed_text` 앞에 `[문서명 > 제목]`. `text`는 동일 → 문맥 보존 효과만 분리해서 측정 |

- 모든 전략이 같은 본문을 받아요. 용어집 dicId 목록과 약관 "출처 목록" 부록은 양쪽 모두 제외했어요.
- 정답 연결: recursive 청크는 **겹치는 근거 단위**(30자 이상, 짧은 단위는 절반 이상 겹침)의 source_id를 받아요. 모든 전략에서 정답 근거 누락은 0이에요.

## 결과 (검색 = BM25 + Kiwi 형태소, 세트별 검색 범위 준수)

| 전략 | 청크 수 | 길이 p50 | 기본 Hit@1 | 기본 Hit@5 | 기본 Recall@5 | 기본 MRR | 가이드 Hit@1 | 가이드 Hit@5 | 추가 Hit@1 | 추가 Hit@5 | 추가 MRR |
|---|---|---|---|---|---|---|---|---|---|---|---|
| recursive_300_50 | 2240 | 271 | 0.450 | 0.750 | 0.640 | 0.553 | 0.45 | 0.90 | 0.600 | 0.833 | 0.688 |
| recursive_500_50 | 1351 | 464 | 0.483 | 0.683 | 0.592 | 0.561 | 0.65 | 0.85 | 0.683 | 0.883 | 0.748 |
| recursive_800_50 | 875 | 749 | 0.517 | 0.767 | 0.681 | 0.604 | 0.60 | 0.90 | 0.700 | 0.933 | 0.788 |
| **structural_1200** | 1226 | 309 | **0.583** | **0.783** | **0.682** | **0.658** | 0.65 | 0.90 | 0.650 | 0.900 | 0.746 |

## 해석
1. **용어집·약관(기본 세트)에서는 구조 기반이 확실히 우세해요.** 비슷한 길이의 recursive_300(p50 271)과 비교하면 Hit@1 0.450 → 0.583, MRR 0.553 → 0.658이에요. 청크 하나가 정답 근거 단위(용어 1개, 조항 1개)와 정확히 일치해서 다른 조항과 섞이지 않기 때문이에요. recursive 청크는 평균 1.36개의 근거 단위가 섞여 있어요.
2. **Recursive는 BM25에서 클수록 유리해요**(300 → 800: 기본 MRR 0.553 → 0.604). BM25는 질문 단어가 더 많이 들어 있는 긴 청크를 선호하는 경향이 있어서예요. 하지만 청크가 길면 LLM 입력 토큰과 노이즈가 늘어나요. **크기 결론은 임베딩 검색과 답변 품질까지 보고 내려야 해요.**
3. **제목 붙이기는 BM25에서 거의 효과가 없어요**(기본 Hit@1 +2문항, 가이드 −1문항). 같은 문서의 모든 청크에 같은 제목 단어가 붙어서 BM25 입장에서는 구별력이 없어요. 효과는 **벡터 검색**에서 확인해야 해요(가설: 상황 서술형 질문에서 문서 맥락이 임베딩에 도움).
4. **가이드북·추가 세트는 전략 간 차이가 1~3문항 수준**이라 지금은 결론을 내리지 않아요. 이 세트는 로더(레이아웃 처리)의 효과가 더 큰데, BM25로는 읽기 순서 개선 효과가 잘 드러나지 않아요.

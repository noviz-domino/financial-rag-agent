금융문서 청킹 파이프라인 안내서

PDF 23개를 "검색하기 좋은 조각(청크)"으로 만드는 과정을 단계별로 설명해요. RAG 전체 중 청킹까지 구현한 상태이고, 검색·답변·Agent·평가 루프는 다음 단계예요.

바쁘면 이것만
  1. 약관·용어집은 쉬워요. 1단 텍스트라 그대로 읽어도 깨끗해요. 어려운 건 가이드북·추가 PDF(펼침면, 2단, 표, 차트)예요.
  2. AI 비용은 그림 처리에만 써요. 읽는 순서·표는 좌표 규칙으로 무료 처리하고, 남은 그림만 Gemini로 글로 바꿔요.
  3. 지금 유력 후보는 Parent-Child 청킹이에요. 작은 조각으로 찾고 큰 덩어리를 LLM에 넘겨요. 최종 결론은 임베딩 검색까지 본 뒤에 내요.
  4. 다른 라이브러리(pymupdf4llm)와도 비교했어요. 표는 그쪽이 더 잘 뽑아서 가져왔고, 읽는 순서·세로 라벨은 우리 로더가 나아서 그대로 뒀어요.

팀원이 지금 할 일: 내 청크를 09 팀 작업 규칙 형식으로 넣고 python -m src.check_chunks 실행 → 같은 표에서 비교. 모르는 단어는 바로 아래 용어 풀이를 펼쳐 보세요.

용어 풀이 (처음 보는 단어가 있으면 펼치기)
청크(chunk)
검색 단위로 잘라 둔 글 조각. 질문이 오면 이 조각들 중 관련 있는 것을 찾아 LLM에 넘겨요.
RAG
질문 → 문서에서 근거 검색 → 근거를 보고 답변. 모델이 아는 것 대신 문서에 적힌 것으로 답하게 하는 방식이에요.
BM25
질문 단어가 많이, 드물게 들어 있는 조각을 위로 올리는 키워드 검색. AI·API가 필요 없어서 비용 0으로 채점할 수 있어요.
임베딩(벡터) 검색
글의 "뜻"을 숫자 목록으로 바꿔 가까운 것을 찾는 검색. 단어가 달라도 뜻이 같으면 찾아요. API 키를 정한 뒤 비교할 예정이에요.
Hit@k · MRR
Hit@5 = 상위 5개 안에 정답 근거가 있는 문항 비율. MRR = 첫 정답의 등수 점수 평균(1등 1.0, 2등 0.5, 3등 0.33…).
source_id
정답지에 적힌 근거 위치 코드(예: fss-life-guide-pdf-10 = 가이드북 10쪽). 청크마다 붙여 두면 자동 채점이 돼요.
OCR
이미지 속 글자를 읽어 텍스트로 바꾸는 것. 여기서는 Windows 내장 OCR을 써요(무료).
VLM · Gemini
이미지를 보고 글로 설명하는 AI 모델. 차트·흐름도를 Markdown으로 바꾸는 데만 써요(유료, 결과는 캐시).
lossy 표
표를 칸으로 나눌 때 값이나 행 이름이 빠진 표. 그대로 쓰면 틀린 답의 원인이 돼서 따로 표시해요.
펼침면 · 2단
펼침면 = A4 두 장이 한 페이지에 붙은 것. 2단 = 신문처럼 한 페이지에 글이 두 줄기로 흐르는 것. 둘 다 그냥 읽으면 좌우 문장이 섞여요.
Parent-Child
작은 조각(child)으로 정밀하게 찾고, 그 조각이 속한 큰 덩어리(parent)를 LLM에 넘기는 구조.

01 · PDF에서 글자 꺼내기

PDF는 "이 위치에 이 글자를 찍어라"라는 명령 모음이에요

그래서 글자마다 내용 + 좌표 + 글자 크기를 꺼낼 수 있어요. pdfplumber로 페이지 단위로 읽어요.

왜

답변에 "파일명 + 페이지"를 표시해야 해서, 처음부터 글자가 몇 페이지에서 왔는지 기억해 둬요.

어떻게

page.extract_text()로 페이지마다 글자를 위→아래로 이어 붙여요.

결과

23개 PDF, 490페이지. 한 페이지가 한 줄인 JSON 파일.

{"file": "06_연금저축계좌설정약관.pdf", "page": 5, "doc_type": "terms",
 "text": "제17조(부득이한 인출)\n① 가입자가 다음 각 호의 ..."}

doc_type은 문서 종류예요(용어집/약관/가이드북/추가). 나중에 "기본 질문은 용어집과 약관에서만 검색"처럼 검색 범위를 나눌 때 써요.

02 · 정답 위치 연결

정답지에 "암호"로 적힌 근거 위치를 풀었어요

정답 파일에는 근거가 fsc-glossary-1697 같은 코드로만 적혀 있어요. 이게 PDF의 어디인지 연결해 둬야 검색 결과를 자동으로 채점할 수 있어요.

질문: 휴면성 증권계좌는 어떤 계좌인가요?
근거: fsc-glossary-1697     ← 이게 PDF의 어디?

코드의 규칙은 PDF 안에 있었어요

용어집과 약관 PDF 맨 끝에 "출처 목록"(각 항목을 가져온 웹 주소)이 있어요. 거기 적힌 번호가 코드와 같아요.

문서코드 예시뜻근거 단위
용어집fsc-glossary-1697출처 목록 주소의 dicId=1697 = "휴면성 증권계좌"용어 1개
약관kofia-terms-121-1789-014주소의 seq=121&historySeq=1789 + 출처 목록 14번째 항목조항 1개
가이드북fss-life-guide-pdf-10PDF 10페이지페이지 1개
추가 PDFhousing_pension_2026-pdf-15그 파일 15페이지페이지 1개

이렇게 PDF를 근거 단위로 잘라 원문 그대로 저장하고 코드만 붙였어요(요약 아님, AI 사용 안 함). 정답 근거 251개 전부 연결돼요.

실제로 있었던 실수
처음엔 약관 코드 끝 숫자를 "조항 번호"로 추측했어요(014 = 제14조). 그런데 약관에는 제10조의2 같은 조항이 끼어 있어서, 출처 목록 순서와 조항 번호가 중간부터 어긋나요. 그래서 "결제불이행" 질문의 근거가 엉뚱한 "제14조(과다호가부담금)"에 연결됐어요. 정답 답안의 핵심어가 연결된 원문에 들어 있는지 내용으로 검증하다가 발견했고, 지금은 출처 목록을 직접 읽어서 연결해요(32개 수정).
교훈: "다 연결됐다(누락 0)"는 "맞게 연결됐다"는 뜻이 아니에요. 내용까지 확인해야 해요.
03 · 읽는 순서 정리

사람 눈으로 읽는 순서대로 글자를 다시 줄 세워요

기본 추출은 같은 높이에 있는 글자를 한 줄로 이어 붙여요. 그래서 좌우가 나뉜 페이지는 문장이 섞여요.

기본 추출(가이드북 p.10):
재무설계를 할 마음의 준비가 되셨나요? ...생애재무설계를 지 3억원을 모으겠다.'와 같이 구체적인...
└──────────── 왼쪽 18쪽 ────────────┘ └──────────── 오른쪽 19쪽 ────────────┘
문제예시해결 방법 (전부 좌표 규칙, 무료)
펼침면가이드북 41쪽, 보험약관 7쪽가로가 세로보다 길면 반으로 잘라 왼쪽·오른쪽을 따로 읽기
2단 본문한국은행 PDF단 사이의 빈 세로줄을 찾아 왼쪽 단 → 오른쪽 단 순서로 읽기
굵은 글씨가 두 번 찍힘1100..55%% → 10.5%같은 위치에 겹친 글자 제거(dedupe_chars)
각주 번호(위첨자)16.5²) → 16.52)로 오염본문보다 훨씬 작은 숫자·괄호 제거
머리말·꼬리말·워터마크"이 문서는 한국은행의 자산으로…"여러 페이지 위·아래에 반복되는 줄 제거
세로로 쓴 글자사이드바 "금융안정상황", 표 옆 "가입 가능"지우지 않고 [세로] 가입가능처럼 한 줄로 보존 (매 페이지 반복되는 사이드바는 위 규칙이 제거)

결과: 약관·용어집은 변화 없음, 가이드북·추가 PDF는 문장이 끊기지 않고 이어져요. 538개 영역(펼침면은 반쪽씩).

다른 라이브러리와 비교: pymupdf4llm

"직접 만든 규칙보다 이미 있는 라이브러리가 낫지 않을까?"를 확인했어요. pymupdf4llm은 PDF를 LLM용 Markdown으로 바꿔 주는 라이브러리이고, 2.x부터 AI 레이아웃 모델로 제목·표·그림 영역을 알아봐요. 문제가 됐던 3쪽을 나란히 놓고 봤어요.

04 · 표 처리

표는 Markdown 표로 바꾸고, 값이 빠졌으면 표시해요

pdfplumber의 표 찾기로 행·열을 읽어 Markdown으로 바꿔요. 그런데 병합 칸·음영 칸이 있으면 값이 조용히 빠져요.

그래서 "손실 검사"를 해요

표 영역의 원문 글자와, 표로 바뀐 뒤의 글자를 비교해요. 한글(행 이름)과 숫자(값)를 따로 세서, 어느 쪽이든 10% 넘게 빠지면 "손실 표"로 표시해요.

  • 깨끗한 표 → Markdown 표로 청크에 넣음
  • 손실 표 → 원문 텍스트는 본문에 그대로 두고, 그림 단계에서 Gemini가 다시 읽음
왜 한글과 숫자를 따로 세나
숫자가 많은 표에서 행 이름 "적립금"(3글자)이 빠져도 전체 비율로는 10% 안쪽이라 못 잡았어요. 따로 세니까 잡혔어요.

lossy 표는 pymupdf4llm 표로 무료 대체 (v3)

같은 쪽에서 pymupdf4llm이 뽑은 표가 아래를 모두 만족할 때만 바꿔 끼워요. 하나라도 어긋나면 원래대로 lossy로 남겨서 Gemini가 다시 읽어요.

  • 원문 한글의 90% 이상이 표 안에 있음 (행·열 이름이 안 빠짐)
  • 원문 숫자 토큰의 95% 이상이 그대로 있고, 표의 숫자 95% 이상이 원문에 있음
  • 표 글자의 80% 이상이 이 표 자리에서 옴 (옆 표나 본문을 끌어오지 않음)
  • 세로 라벨이 붙은 표(72쪽 같은)는 바꾸지 않음

결과: lossy 표 134개 → 33개. 대체한 표는 청크의 source에 pymupdf4llm으로 표시돼요.

"글자"가 아니라 "숫자 토큰"으로 세는 이유
퇴직연금 22쪽 표에서 합계 247,738이 24 | 7,738로 두 칸에 잘못 나뉜 표가 있었어요. 숫자 글자는 하나도 빠지지 않아서 처음 검사를 통과했는데, 값은 틀렸어요. 숫자를 247,738 같은 덩어리 단위로 비교하니 걸러졌어요. 또 각주 위첨자 16.5²)가 16.52)로 붙는 문제도 같은 검사로 발견해서 고쳤어요.
05 · 그림 처리

그림을 잘라서, OCR로 거르고, 필요한 것만 Gemini가 글로 바꿔요

PDF 속 "그림"은 두 종류예요. 사진처럼 붙인 이미지와, 선·상자를 그리는 명령으로 만든 벡터 그림. 벡터 그림은 이미지가 아니라서 "이미지만 자르기"로는 놓쳐요.

그림 종류찾는 방법예시
이미지(래스터)PDF 속 이미지 위치. 겹친 이미지는 하나로 합침74조각으로 잘려 있던 자영업자 차트가 한 장으로
벡터 차트·도식선·상자·곡선 좌표를 묶어서 영역 찾기 (아래 규칙)한국은행 차트, 주택연금 72쪽 단계표
흐름도작은 이미지(화살표)가 3개 이상 모인 곳주택연금 41쪽 가입 절차
손실 표4단계에서 값이 빠진 표정책서민금융 [표 1] 가계신용 추이

어디를 자를지는 Gemini가 아니라 좌표 규칙이 정해요

① 선·상자·곡선 위치를 모두 모음 (배경 상자, 깨끗한 표의 칸 테두리는 제외)
② 4pt 안으로 붙은 도형끼리 묶음 (3개 이상인 묶음만)
③ 30pt 안으로 가까운 묶음끼리 다시 합침 → 합친 뒤 도형 15개 이상이면 그림
④ 그림에 바로 붙은 표도 합침 (사이에 "[표 …]", "그림 …" 캡션이 있으면 별개라 안 합침)
⑤ 옆에 세로로 쓴 라벨("가입 가능" 등)이 40pt 안에 있거나 경계에 걸쳐 있으면 포함
⑥ 축 라벨이 들어오게 15pt, 위쪽 범례·제목 줄까지 최대 60pt 넓힘
⑦ 안에 글자가 있어야 후보 (텍스트 숫자 4개 이상 / 단어 8개 이상 / OCR 글자 10자 이상)

OCR 라우터: AI에 보내기 전에 거르기

Windows 내장 OCR(이미지 2배 확대)로 모든 후보의 글자를 먼저 읽어요. 한 장에 0.16초, 비용 0원이에요.

  • 살림: 글자를 도형으로 바꿔서 텍스트로는 비어 보이던 차트 (퇴직연금 17쪽 점유율 그래프)
  • 뺌: 같은 이미지가 3번 이상 반복되고 OCR에도 새 글자가 없는 것 (FAQ 제목 배너 100개)
  • 뺌: 작고 글자 없는 이미지 (QR 코드, 로고)
OCR 엔진 (205개 자동 채점)1장당글자 재현율숫자 재현율
EasyOCR ×25.11초0.8650.740
Windows OCR ×2 (채택)0.16초0.8520.766
RapidOCR처음엔 보안 정책이 shapely DLL을 막아 실행 불가. 지금(10/20 재확인)은 실행되지만 기본 모델이 중국어·영어라 한글을 못 읽음
Tesseract미설치 (별도 설치 파일 + 한국어 데이터 필요)

Gemini: 남은 그림만 Markdown으로

그림 후보 438개 중 장식·중복을 빼고 316개만 Gemini(gemini-2.5-flash)로 보냈어요 (반복 배너 100개, 글자 얹힌 배경 19개, QR·로고 3개 제외). 변환 316개 · 오류 0개. 숫자 검증 0.9 이상 188개, 0.5 미만 17개, 원문에 없는 숫자 경고가 붙은 그림 89개. 전체 비용은 입력 약 23만·출력 약 49만 토큰이었어요.

Gemini가 쓴 숫자가 원문(텍스트·OCR·캡션)에 실제로 있는지 숫자 검증을 해요. 원문에 없는 숫자는 청크에 ※ 원문에 숫자로 적혀 있지 않은 그래프 판독값(인용 주의) 경고를 붙여요. 선그래프 높이를 눈대중으로 읽은 값일 수 있어서예요.

사례: 주택연금 72쪽 (재건축 단계별 가입 가능 여부)

수정 전

  • 위쪽 절반만 잘림: 빨간 테두리(가입 가능)가 상자들을 묶어 줘서 그림으로 잡혔지만, 아래쪽은 테두리 없이 행마다 작은 상자(도형 3~5개)라 기준(15개)에서 탈락
  • 왼쪽 "가입 가능 / 불가" 라벨이 잘림: 라벨은 글자라서 도형 묶기 대상이 아니고, 옆의 회색 막대는 상자들과 30pt 넘게 떨어진 사각형 1개라 묶음에 안 들어감. 영역이 상자 왼쪽 끝(x=66)에서 시작해 라벨(x 61~69)이 반쯤 잘림
  • pdfplumber 표는 두 열만 잡혀 업무내용 열 누락, 칸이 두 행으로 쪼개짐
  • 같은 내용이 표 청크와 그림 청크에 중복

수정 후

  • 작은 상자 묶음도 남기고(③), 맞닿은 표까지 합쳐서(④) 표 전체를 한 그림으로
  • 세로 라벨 규칙(⑤): 그림 옆이나 경계에 걸친 세로 글자를 영역에 포함 → 라벨이 반드시 들어감
  • Gemini 결과에 가입가능 6단계 / 가입불가 4단계, 단계 사이 →, 업무내용 전부
  • 결론 문장: "사업시행인가까지 가입 가능, 관리처분계획 인가부터 불가"
  • Gemini가 덮은 pdfplumber 표는 청크에서 뺌
라벨이 잘렸던 진짜 이유
글자가 흐려서가 아니에요. 자르는 범위를 "도형 묶음"으로 정하는데, 라벨은 도형이 아니라 글자라서 범위 계산에 들어가지 않았어요. 중간 수정 때는 표 영역이 왼쪽으로 조금 넓어서 우연히 라벨까지 들어갔고, 그래서 우연에 기대지 않도록 세로 라벨을 일부러 포함하는 규칙(⑤)을 따로 만들었어요.
그림 밖의 예외 문장
표 아래 "단, 신탁방식의 경우 조합설립인가 전까지 가입 가능"은 그림 영역 밖이라 본문 청크에 있어요. 7단계의 Parent-Child 구조 덕분에 LLM에는 72쪽 전체가 함께 넘어가서 이 예외도 같이 봐요.
06 · 청킹

문서를 검색하기 좋은 크기로 자르는 방법 4가지를 비교했어요

전략자르는 방법특징
Recursive (300 / 500 / 800자)글자 수 기준으로 자름 (겹침 50자)가장 단순한 기준선. 조항 중간이 잘릴 수 있음
구조 기반용어집 = 용어 1개, 약관 = 조항 1개(길면 ①② 항 단위), 가이드북·추가 = 제목·글머리표 단락정답 근거 단위와 맞아서 섞임이 없음
구조 + 그림구조 기반에 표·그림 청크를 따로 추가표·차트 질문에 대응
Parent-Child작은 조각(child)으로 검색, 큰 덩어리(parent)를 LLM에 전달검색은 정밀하게, 답변은 문맥과 함께

모든 전략이 같은 본문을 받아요(용어집·약관 끝의 출처 목록은 모두 제외). 그래야 공정한 비교예요.

09 · 팀 작업 규칙

각자 만든 청크를 한 표에서 비교하려면

청크 파일을 아래 형식으로 data/chunks/{이름}_{전략}.jsonl에 넣으면 python -m src.check_chunks 한 번으로 같은 표에 나와요.

필수 필드: chunk_id, text, embed_text, file, pages, doc_type, source_ids
권장 필드: content_type, page, chunk_index, title, parent_id
점수가 높게 나와도 조심할 점
지금까지 설정은 제공 질문 세트를 보면서 골랐어요. 같은 문제로 고르고 같은 문제로 채점하면 새 질문에서는 점수가 떨어질 수 있어요. 그래서 제공 세트 = 개발용, 팀이 직접 만드는 골든셋 = 최종 확인용(설정을 다 정한 뒤 한 번만 평가)으로 나눠요. 골든셋은 근거를 "파일명 + 페이지"로 적어 두면 같은 방식으로 채점할 수 있어요.

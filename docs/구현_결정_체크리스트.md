# 구현 결정 체크리스트

> 위에서부터 순서대로 정해요. 앞 단계의 결정이 뒤 단계의 입력이 되기 때문이에요.
> 각 항목: **정할 것 → 보기 → (참고) 사전 실험에서 확인한 것 → 결정 칸**
> ⭐ = 사전 실험(개인 폴더 `rag_mini_project`)에서 효과를 확인한 쪽

## 전체 순서
| 단계 | 주제 | 핵심 질문 |
|---|---|---|
| 0 | 공통 환경 | 어디서, 무엇으로, 어떤 설정 방식으로 실행하나 |
| 1 | PDF 로딩 | 어떤 라이브러리로, 어떤 단위로, 읽는 순서를 어떻게 맞추나 |
| 2 | 표 | 어떻게 추출하고, 어떤 형식으로 바꾸고, 실패는 어떻게 판정하나 |
| 3 | 이미지·차트·도식 | 무엇을 후보로 잡고, 무엇을 버리고, 무엇을 Gemini에 넘기나 |
| 4 | 정답 위치 연결 | 검색 결과를 어떻게 자동 채점하나 |
| 5 | 청킹 | 어떤 단위·크기로 자르고, 어떤 정보를 붙이나 |
| 6 | 임베딩·인덱스 | 어떤 모델로, 무엇을, 어디에 저장하나 |
| 7 | 검색 | 어떤 방식으로, 몇 개를, 어떤 형식으로 돌려주나 |
| 8 | 답변 생성 (기본 RAG) | 어떤 프롬프트로, 어떤 출력 형식으로 답하나 |

## 1. PDF 로딩

### 1-1 라이브러리
| 보기 | 장점 | 단점 |
|---|---|---|
| ⭐ **pdfplumber** | 글자마다 좌표·크기를 줌 → 규칙을 정밀하게 짤 수 있음, 표 추출 내장 | 다단·펼침면은 직접 규칙을 짜야 함 |
| **pymupdf4llm** | 바로 Markdown, 제목(#) 자동, 다단 처리 | AGPL 라이선스, 이 PC 보안 정책에 막히는지 확인 필요, 세로 라벨·펼침면 처리 미확인 |
| PyMuPDF (fitz) | 빠르고 블록 단위 정보 | 정밀 규칙은 직접 |
| pypdf / pypdfium2 | 가볍고 빠름 | 좌표·구조 정보 거의 없음 (비교용 기준선) |
| docling / MinerU (로컬 레이아웃 모델) | 제목·본문·표·그림을 모델이 구분 | 설치가 무겁고 GPU 권장 (이 PC: RTX 4060 8GB) |
| Upstage Document Parse (API) | 한국어 문서 구조 복원이 강점 | 유료, 외부 전송 |

> 참고: 약관 15개·용어집은 **1단, 이미지 없음**이라 어떤 라이브러리로도 깨끗하게 읽혀요. 차이는 가이드북·추가 PDF에서 나요.

### 1-2 읽는 단위
| 보기 | 설명 |
|---|---|
| 페이지 | 가장 단순. 정답 ID가 페이지 기준이라 연결이 쉬움 |
| ⭐ 반쪽 페이지 | 가이드북 41쪽·보험약관 7쪽은 A4 두 장이 붙은 **펼침면** → 좌우를 나눠야 문장이 안 섞임 |

### 1-3 읽는 순서·노이즈 규칙 (가이드북·추가 PDF)
| 문제 | 판정 조건 보기 | 사전 실험 |
|---|---|---|
| 펼침면 | 가로 > 세로 × 1.15 → 반으로 자르기 | ⭐ 정확 |
| 2단 본문 | 가운데 세로 여백을 **가로지르는 줄**이 30% 미만이면 2단 | 단어 수 기준으로 하면 1단도 2단으로 오판했음 |
| 굵은 글씨 겹침 | `dedupe_chars()` | `1100..55%%` → `10.5%` 복원 |
| 각주 위첨자 | 본문 글자 크기의 65% 미만인 숫자·괄호 제거 | 표 속 `16.5²)`가 `16.52)`로 오염되던 것 해결 |
| 머리말·꼬리말 | 페이지 위·아래 3줄 안에서 30% 이상 페이지에 반복 | 본문 속 `자료: 한국은행…`까지 지우지 않게 위치 제한 |
| 세로 글자 | 지우기 / ⭐ `[세로] 가입불가`처럼 한 줄로 보존 | 사이드바는 반복 규칙이 제거, 표 라벨은 남음 |

### 1-4 출력 형식

 "printed_page": 18, "text": "...", "tables": [...], "figure_lines": [...]}

## 3. 이미지·차트·도식
### 3-1 후보를 어떻게 찾나
| 종류 | 찾는 방법 보기 | 사전 실험 |
|---|---|---|
| 이미지(래스터) | PDF 이미지 객체 위치, 겹친 이미지는 합침 | 74조각으로 잘린 차트가 한 장으로 합쳐짐 |
| 벡터 차트·도식 | 선·상자·곡선 좌표를 묶기: 4pt 안 → 30pt 안 → 합친 뒤 도형 15개 이상 | **이미지만 자르면 놓침** (한국은행 차트는 전부 벡터) |
| 흐름도 | 작은 이미지(화살표) 3개 이상이 40pt 안에 모임 | 주택연금 41쪽 절차 |
| 맞닿은 표·옆 라벨 | 그림에 붙은 표, 옆 세로 라벨까지 포함 (사이에 캡션 줄 있으면 분리) | 72쪽이 위쪽 절반만 잘리던 문제 해결 |

### 3-2 "어디가 그림인지"를 누가 판단하나 ⭐ 가장 큰 결정
| 보기 | 비용 | 정확도·특징 |
|---|---|---|
| ⭐ **좌표 규칙** (위 3-1) | 0원 | 문서 디자인이 바뀌면 놓치는 경우가 생김 → 표본 확인 필요 |
| **로컬 레이아웃 모델** (docling, PP-DocLayout, DocLayNet YOLO, PaddleOCR-VL) | 0원 (GPU 사용) | 제목·표·그림 영역을 모델이 판단. 설치·속도 확인 필요 |
| **Gemini가 페이지 전체를 보고 판단** | 페이지마다 호출 | 가장 단순하지만 490쪽 전부 호출 |

### 3-3 무엇을 버리나 (AI 호출 전 거르기)
| 조건 보기 | 사전 실험 |
|---|---|
| 페이지 면적 2% 미만 | |
| 같은 원본 이미지가 문서에 3번 이상 **그리고** OCR에도 새 글자 없음 | FAQ 제목 배너 100개 제외 (질문 글자는 텍스트로 이미 있음) |
| 큰 이미지 위에 글자가 30단어 이상 얹힘 | 배경 이미지 19개 제외 |
| 면적 5% 미만 + OCR 글자 15자 미만 | QR 코드·로고 |

### 9-1 형태
| 보기 | 특징 |
|---|---|
| ⭐ LangGraph 그래프 (직접 노드 설계) | 노드·분기가 곧 구조도 제출물 |
| ReAct(툴 호출 Agent) | 빠르지만 흐름이 불투명 |
| 직접 while 루프 | 의존성 없음, 구조도는 따로 그림 |

### 9-2 노드 후보 (고르기)
```
route(질문 유형·안전 판단) → make_query(검색어) → retrieve → grade(근거 충분?)
   ├ 충분 → generate → verify(인용·숫자 확인) → END
   ├ 부족·재시도 남음 → rewrite → retrieve
   └ 부족·재시도 끝 → abstain → END
route → refuse / clarify → END
```
| 노드 | 구현 보기 |
|---|---|
| route | LLM 구조화 출력 / 규칙(키워드) / 결정 모델(Jev 등) |
| grade | 청크 묶음 한 번에 판정 / 청크별 판정 / 리랭커 점수 임계값 |
| rewrite | 부족한 정보 기반 재작성 / 약어 확장 / 여러 검색어 |
| verify | 규칙(인용 존재·숫자 원문 대조) / LLM / 생략 |

| 재생성 최대 | 1회 |

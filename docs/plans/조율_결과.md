## 한눈에 보는 추천 구성
고르는 순서: ① 누가 **실제로 만들고 측정**했나 → ② **비용**(특히 LLM 호출) → ③ 의견 표 수.

```
PDF 23개
 └ [1 로딩]   pdfplumber + 펼침면만 반쪽 분할 + noviz 규칙(2단·머리말·위첨자·세로 라벨) + jjh 규칙(cid 깨짐·PUA 글리프 복구)
 └ [2 표]     find_tables → 손실이면 pymupdf4llm 표 → 그래도 손실이면 Gemini   + jjh의 병합 칸 채우기·긴 표 행 분할
 └ [3 그림]   좌표 규칙으로 후보 → 규칙 필터 → Windows OCR → Gemini(캐시 공유) → 숫자 자동 검증 → 낮은 것만 사람 검수(jjh 방식)
 └ [4 정답]   출처 목록 기반 source_id 연결(누락 0) + page_hit 함께 계산
 └ [5 청킹]   기준 structural(용어·조항·제목) / 비교 recursive_500_50·parent-child / 링크는 메타데이터로 보관
 └ [6 인덱스] gemini-embedding-001 + 벡터 저장소(numpy로 시작, 인터페이스 뒤에 숨김), doc_type 범위 강제
 └ [7 검색]   하이브리드 BM25(Kiwi) + 벡터, RRF 60, k=5          ← 3/3 같은 선택
 └ [8 답변]   jjh의 "근거 판단(JSON) → 답변" 2단계 + 행동 분류 + 공통 근거 규칙(<doc> 감싸기, 인용 주의 수치)
 └ [9 Agent]  LangGraph 최소 그래프(route → retrieve → grade → rewrite≤2 → generate → verify) 먼저, 링크 확장은 2차
 └ [10 평가]  jjh 평가 루프(runs/, 실패 분류) 공용화 + noviz 검색 지표 + 채점 모델 분리·사람 20문항   ← 3/3 동의
```

### 꼭 정해야 하는 것

**1. 처음 기본 버전을 어떻게 만들까?** (쟁점 ⑨)
- 왜 묻나: 실험은 "기본 버전 하나를 만들고, 한 군데씩 바꿔 보며 비교"하는 방식이에요. 출발점이 정해져야 실험을 시작할 수 있어요.
- 추천: **문서를 조항·용어 단위로 자르고, 뜻이 비슷한 글을 찾는 방식(벡터 검색)**으로 시작해요. 세 명 중 두 명이 고른 방식이에요. 단어를 그대로 맞춰 찾는 방식을 섞는 건(하이브리드) 나중에 "바꿔 보는 실험"으로 효과를 보여 줘요.

**2. 그림을 글로 바꾼 결과는 누구 걸 쓸까?** (쟁점 ④)
- 왜 묻나: PDF 속 그래프·그림을 AI(Gemini)가 글로 바꿔 둔 결과가 noviz님 것(316개)과 jjh님 것(65개)으로 따로 있어요.
- 추천: **많이 바꿔 둔 noviz님 것을 쓰고**, AI가 숫자를 틀린 걸 사람이 찾아 고치는 건 **jjh님 방식**으로 해요. jjh님이 이미 고친 4개도 반영해요. 이 결과 파일은 다시 만들면 돈이 드니까 팀원끼리 나눠 가져요.

**3. 검색용 데이터를 어디에 저장할까?** (쟁점 ⑥)
- 왜 묻나: noviz님·yellow님은 전용 프로그램(Chroma)을, jjh님은 간단한 파일 저장(numpy)을 골랐어요.
- 추천: 문서 양이 적어서 **간단한 방식(numpy)으로 충분**해요. jjh님 코드는 이미 돌아가요. 나중에 필요하면 Chroma로 바꿀 수 있게 만들어 둬요.

# 실험 계획

## 목적
기준 설정 하나를 정해 두고 **한 번에 한 가지만** 바꿔서, 무엇이 실제로 도움이 되는지 숫자로 보여 줘요. 특히 **정확도와 토큰(비용)을 같이** 봐서, 차이가 작으면 싼 쪽을 고르는 게 목표예요.

## 기준 설정 (`configs/baseline.json`)
| 항목 | 값 |
|---|---|
| 청킹 | 구조형, 최대 1,200자, 100자 미만 절은 합침 |
| 검색 | 하이브리드 (BM25 + 벡터, RRF 60), k = 5 |
| 임베딩 | gemini-embedding-001, 768차원, `text` |
| 답변 | 근거 판단 → 답변, gemini-2.5-flash, temperature 0 |
| 채점 | gemini-2.5-pro + 규칙 |

## 고정 조건
질문 세트(180문항, 세트별 검색 범위 지킴), 채점 방법, 답변 모델·프롬프트는 **바꾸는 항목이 아니면 그대로** 둬요. 결과는 세트별로 따로 집계해요.

## 비교 조건과 숫자를 고른 이유

### A. 청킹 — 방식마다 조건 3개
**공통 원칙**: 현재 쓰는 값을 가운데 두고 **더 작게 / 더 크게** 하나씩. 작은 쪽은 "토큰을 줄여도 정답을 잘 찾나", 큰 쪽은 "덜 쪼개면 정답이 덜 잘리나"를 봐요.

| 방식 | 조건 | 가운데 값의 출처 | 양쪽 값을 고른 이유 |
|---|---|---|---|
| 글자 수 자르기 (recursive) | **300 / 500 / 800자**, 겹침 **100** | 500: 과제 체크리스트 예시, jjh `recursive_500_50`, noviz 기준선 | 300·800은 noviz가 예전에 비교하던 값 (BM25에서 길수록 MRR 0.570 → 0.621, 벡터에서 재확인 필요) |
| 구조형 (structural) | 최대 **800 / 1,200 / 1,600자** | 1,200: noviz 구현 (넘으면 항 단위로 분할) | ±400자. 800은 긴 조항이 더 쪼개지는 대신 토큰↓, 1,600은 덜 쪼개지는 대신 토큰↑ |
| parent-child | child **300 / 400 / 600자** | 400: 체크리스트 5-5, noviz 구현 | 300은 더 정밀하게 찾기, 600은 구조형에 가까운 크기 |

**겹침을 100으로 통일한 이유**
- 50자는 PDF 한 줄(약 100자)보다 짧아서, 줄 단위로 자르는 코드에서 **실제로 겹침이 생기지 않았어요** (버그, [05](05_실패사례_개선.md) F2).
- 100자는 약 한 줄이라 문장이 경계에서 잘려도 앞뒤 청크 중 하나에는 온전히 남아요.
- 세 크기에 같은 겹침을 써야 **크기만의 효과**를 볼 수 있어요. (비율로는 300자 33%, 500자 20%, 800자 12.5%)

### B. 검색 개수 k — 3 / 4 / 5
- 5: 현재 기준 (체크리스트·세 사람 모두 5).
- 3·4: 토큰을 줄이려는 목적. 구조형 청크 5개 ≈ 3,000자라 3개면 약 40% 줄어요.
- 10은 제외: 토큰만 늘고 목적(최적화)과 반대예요.
- **걱정되는 점**: BM25에서 Hit@1 0.622 vs Hit@5 0.851 → 정답이 2~5위에 걸린 경우가 많아요. 정답 근거가 2개 이상인 문항도 많아요(기본 positive 60문항 중 26개). k를 줄이면 Recall이 떨어질 수 있어요.

### C. 임베딩 모델 — gemini-embedding-001 / gemini-embedding-2
- 001: 조율 때 실제로 써 본 모델.
- 2: 2026-04 정식 출시. 강점은 멀티모달(이미지·PDF)인데, 우리는 그림을 글로 바꾼 뒤 텍스트만 임베딩해요. 그래서 **텍스트 검색에서도 나은지**를 재요.
- 차원은 둘 다 768로 맞춰서 모델 차이만 봐요.

### D. 그 밖의 실험 (기획서 6장)
| 실험 | 바꾸는 것 |
|---|---|
| 0 흔들림 | 기준을 같은 조건으로 2번 (답변 단계. 검색은 결정적이라 흔들림 없음) |
| 2 검색 방식 | 하이브리드 → 벡터만 / BM25만 |
| 3 구조 | 기본 RAG → Agent |
| 4 문맥 | `text` → `embed_text` (`[문서 > 장 > 절]` 접두어) |
| 마지막 | 골든셋 30문항, 설정 확정 후 1번 |

## 진행 순서와 비용
1. **검색 지표만** (`--retrieval-only`, 148문항): A·B·C 전부. 답변·채점 AI를 안 불러서 비용은 청크·질문 임베딩뿐.
2. 위 표에서 **상위 2~3개 설정만** 답변까지 실행해 답변 점수·토큰 비교.
3. 기준 확정 → 실험 0, 2, 3, 4 → 골든셋.

## 지표와 판단 기준
- 검색: Hit@1, Hit@k, Recall@k, MRR (정답 근거 ID 기준 + 쪽 기준)
- 비용: 질문당 근거 글자 수·토큰, AI 호출 수, 시간
- **판단**: 차이가 흔들림(실험 0)보다 작으면 **토큰이 적은 쪽**을 고름.
